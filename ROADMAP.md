# Roadmap

Build plan for the enterprise RAG backend. Status reflects the actual state of the code, checked against each phase — not just intent.

Guiding philosophy (keep following this): **don't build phases ahead of need.** Learn and implement just enough to complete the feature in front of you. While building uploads, don't discuss embeddings. While building embeddings, don't discuss Terraform. This is deliberate, to avoid overload — see the "Intentional design decisions" section in `CLAUDE.md` for a concrete example (empty interface files left empty until a second implementation actually needs them).

## Immediate next candidates (in rough order)

1. A fourth document source with real structure to parse (e.g. DOCX, CSV/Excel, or a real connector) — plain text/Markdown didn't need source-specific `Cleaner`/`Chunker` handling since it's just a UTF-8 decode, so the interface question is still open; a source with actual structure (tables, headers) would be the real trigger
2. Citations & Memory (Phase 15) — `PromptBuilder` already tags context with `[n]` reference numbers matched to `chunk_id`/`document_id` in `POST /chat`'s `sources` list, so citation parsing/formatting has something concrete to build on; conversation memory (multi-turn) also isn't started — `POST /chat` is single-turn only today, no history parameter
3. **Explicitly deferred, do not start speculatively:** Query Intelligence (Phase 11), context compression (rest of Phase 12), and hardening the LLM layer (streaming/fallback/retry/cost tracking, other providers) — decided to wait for real usage (`POST /chat` traffic) before building any of these, rather than guessing at behavior with no usage data.

## Decisions log

- **Embedding model is `text-embedding-3-small` (1536 dims), fixed.** Multi-model support later needs either separate vector columns/tables per dimension or a projection step — noted for when Phase 8's provider list expands.
- **`embedding_model` column added to `document_chunks`** ahead of needing multiple providers, specifically so vectors stay traceable to the model that produced them (cheap to add now, expensive to backfill later).
- **`CREATE EXTENSION vector` was missing from migrations** even though the `embedding` column already worked (it had been enabled manually on the dev database at some point). Added to the HNSW index migration so a fresh database built from migrations alone won't fail.
- **`POST /search` returns raw candidate chunks, no ranking/reranking yet.** This is intentionally the "candidate retrieval" stage only (Phase 10) — narrowing to the best few chunks is Phase 12's job (RRF, cross-encoder, MMR), not built yet.
- **`Extractor` is now a real ABC** (`app/pipeline/extractors/extractor.py`) now that webpage ingestion gave it a genuine second implementation (`PDFExtractor`, `WebPageExtractor`). Both now take raw `bytes` rather than a file path — `Cleaner`/`Chunker` stay concrete/undefined, still one implementation each.
- **Fixed a pre-existing bug** in `DocumentChunkService.chunk_document` (`page.cleaned_text`/`page.page_number` — neither attribute exists on `DocumentContent`, which has `clean_text`/`content_order`). This had never been exercised against a live DB, so it was silently broken since it was written; found while building web ingestion.
- **`UrlFetcher` (`app/pipeline/loaders/url_fetcher.py`) added with SSRF guards** for `ingest_url`: scheme allowlist, private/loopback/link-local/reserved IP rejection via DNS resolution, no redirect-following, streamed response with a size cap. Known residual gap: DNS-rebinding between the guard check and the actual connection — acceptable for now, flagged for before this handles untrusted multi-tenant traffic.
- **Webpage dedup is checksum-based, same as PDFs** — re-ingesting an unchanged URL conflicts (409). Detecting that a page's content *changed* since last crawl (versioning/re-crawl) is not built — out of scope for this pass.
- **`document_chunks.search_vector` is a Postgres `GENERATED ALWAYS AS (to_tsvector('english', text)) STORED` column**, not populated in application code, so it can never drift out of sync with `text` regardless of which code path inserts a chunk. Indexed with GIN (not GiST) since chunk text is written once and read many times, mirroring the reasoning behind picking HNSW over IVFFlat for the embedding index. Fixed to `'english'` — adding another language later needs a new migration to redefine the column, not a config toggle.
- **Keyword search uses `websearch_to_tsquery`, not `to_tsquery`/`plainto_tsquery`** — the only one of the three that's both safe on arbitrary free-text user input and supports natural search-box syntax (quoted phrases, `-exclusion`). Ranked with `ts_rank` rather than `ts_rank_cd`, since proximity/cover-density scoring adds cost with little benefit on chunk-sized text.
- **`search_by_keywords` filters to `ChunkStatus.EMBEDDED`, same as `search_by_embedding`**, so both rankers draw from the same candidate pool — otherwise RRF fusion would unfairly favor/penalize chunks that only appear in one list purely because of pipeline stage, not relevance.
- **RRF fusion (`RetrievalService._fuse_rrf`) is unweighted between vector and keyword lists**, with only `rrf_k` (default 60, the standard literature/industry value) exposed as a setting. No per-source weighting added — RRF's appeal is not needing score normalization across cosine distance and `ts_rank`'s different scales; weighting is a knob to add later only if real query data justifies it.
- **Each ranker over-fetches a candidate pool (`retrieval_candidate_pool_size`, default 50) before fusion**, rather than fetching only the client's requested `top_k` from each — otherwise a chunk ranked low in one list but high in the other could get cut before fusion ever sees it.
- **`SearchRequest.created_after`/`created_before` use Pydantic's `AwareDatetime`**, not plain `datetime` — `DocumentChunk.created_at` is timezone-aware, and comparing it against a naive input is a silent-bug source, so ambiguous (no UTC offset) input is rejected at the API boundary instead.
- **`TextExtractor` added for plain text/Markdown** (`app/pipeline/extractors/text_extractor.py`) — just a UTF-8 decode into a single `DocumentContent` (`content_order=1`), no source-specific parsing needed, so it reuses the existing `POST /document/upload` endpoint and the generic `TextCleaner`/`RecursiveChunker` unchanged. Didn't end up being a trigger for `Cleaner`/`Chunker` interfaces since there was no source-specific logic to abstract over.
- **Cross-encoder reranking (`CrossEncoderReranker`, `app/pipeline/reranking/cross_encoder_reranker.py`) runs after RRF fusion narrows the pool**, scoring the fused candidates directly against the query rather than the full unfused vector+keyword pool, since it's the most expensive step per-candidate. Model is `cross-encoder/ms-marco-MiniLM-L-6-v2` (`settings.reranker_model`), loaded via `sentence-transformers`.
- **`PromptBuilder` (`app/pipeline/prompting/prompt_builder.py`) returns OpenAI-style chat messages** (`list[{"role", "content"}]`) rather than a single flattened string, so it hands directly to `OpenAIChat.complete` without reshaping.
- **No standalone `POST /prompt/build` endpoint or `PromptService` wrapper — an initial pass added both, then reversed.** A prompt isn't a complete, usable result on its own (nobody can do anything with it without an LLM to send it to), so exposing it as its own endpoint broke the pattern every other pipeline stage follows in this repo: `Extractor`/`TextCleaner`/`RecursiveChunker`/`CrossEncoderReranker`/`MMRSelector` are all internal components only reachable through their orchestrating service's endpoint, never given their own route. `PromptBuilder` now has its real caller: `ChatService`.
- **No token-budget truncation or context compression in `PromptBuilder` yet** — chunk count is already capped via `top_k`/MMR upstream, and real prompt-length behavior needs actual chunk sizes/models in play to tune against, same reasoning as the Query Intelligence deferral.
- **`ChatService` (`app/services/chat_service.py`) composes `RetrievalService` + `PromptBuilder` + `OpenAIChat` behind `POST /chat`**, mirroring how `RetrievalService` itself composes the reranker/MMR pieces, and how `DocumentService` composes the ingestion pipeline — the orchestrator that has a real caller gets the endpoint, the pieces it composes don't. `POST /chat` returns `{ answer, sources }` in one call, matching `/search`'s "one call, not a chain of calls" shape.
- **`OpenAIChat` (`app/pipeline/llm/openai_chat.py`) is OpenAI-only**, mirroring `OpenAIEmbeddings` — single implementation, so no LLM-client ABC yet (same "wait for a second real implementation" reasoning as `Cleaner`/`Chunker`). Model is `gpt-4o-mini` (`settings.chat_model`), temperature `0.2` (`settings.chat_temperature`, low — favors grounded/factual answers over creativity for a RAG use case) — both defaults unvalidated against real traffic. No streaming, retry/fallback, or cost/token tracking; `POST /chat` is single-turn only (no conversation history param), so multi-turn memory (Phase 15) is a separate gap, not just an oversight here.
- **Context is numbered and source-tagged (`[n] (document {id}, page {page}) {text}`) in the built prompt**, not just concatenated — gives the model citable reference points and gives Phase 15 (Citations) something to anchor `[n]` back to `chunk_id`/`document_id` later, without building a citation system now.
- **MMR (`MMRSelector`, `app/pipeline/reranking/mmr.py`) does the final `top_k` selection**, after cross-encoder reranking, in `RetrievalService.retrieve_candidates`. It's the classic embedding-based formulation — both the query-relevance term and the inter-candidate redundancy term use chunk-embedding cosine similarity (not the cross-encoder score), since mixing an unbounded cross-encoder score with a [-1,1] cosine term would need score normalization the embeddings avoid. Pure Python (dot/sqrt loops), not numpy — the candidate pool going into MMR is capped at `retrieval_candidate_pool_size` (default 50), too small for numpy vectorization to matter, and numpy isn't currently a direct dependency. `settings.mmr_lambda` (default `0.5`) trades relevance vs. diversity; `1.0` is equivalent to no MMR (pure relevance order). Context compression (the rest of Phase 12) not built yet.
